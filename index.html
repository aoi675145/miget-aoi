Rill — a tiny self-hosted WebSocket relay for voice rooms

One process, one port, one WebSocket endpoint. Rill relays audio frames between the members of a room without accounts, databases or a control plane. Bring your own host and you are done.

Self-hosting guide Protocol reference
python ≥ 3.11 websocket only no database ~40 MB resident

How it works

Rill is deliberately small. A client opens one WebSocket, names a room, and from then on the relay only moves opaque frames between the members of that room.

◈

Rooms, not channels

A room exists as long as somebody is in it. Nothing is written to disk, so a restart never leaves stale state behind.

⇄

Relay, not mixer

Frames are forwarded as-is. Rill never decodes audio, so it cannot resample, record or inspect what it carries.

⚡

Binary frames only

Text frames are rejected with close code 1003. Ping and pong are handled by the relay so idle rooms survive NAT timeouts.

◷

Cheap to run

Measured at about 40 MB resident with eight idle rooms, and it never buffers more than one frame per member.

⛨

Rooms are unguessable

The endpoint path is derived from the deployment's own identifier, so there is no directory to enumerate.

⏻

No telemetry

Rill makes no outbound calls of its own. The only network traffic it produces is the audio it relays.

Protocol

Rill speaks plain WebSocket. Anything that can open a socket and send binary frames can use it — the reference client is 30 lines of JavaScript.

StepWhat happens
GET <path> with UpgradeThe handshake completes and the socket becomes the room connection.
GET <path> without UpgradeAnswered with 426 Upgrade Required, so a browser tab hitting the endpoint by accident gets a clear error.
Binary frame inForwarded to every other member of the same room.
Text frame inRejected; the connection closes with code 1003.
Frame larger than the limitConnection closes with code 1009 rather than growing the buffer.
All members goneThe room is dropped immediately.

Self-hosting

Rill is a long-lived process with no build step. If your host can keep a Python process alive, it can run Rill.

  1. Pick an identifier. A deployment identifier decides the endpoint path; every host should use its own.
  2. Set the port. Most platforms hand a port through the environment.
  3. Run it. Foreground is fine — Rill only serves, it has nothing to reconnect to.
  4. Point clients at it. wss://your-host/<path>, binary frames, done.
  5. Check it stays up. /health answers with two bytes, which is plenty for an uptime monitor.
# install
git clone https://github.com/rill-relay/rill.git
cd rill
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt

# configure
cp .env.example .env
$EDITOR .env

# run
python relay.py

# .env
RELAY_ID=           # endpoint path seed, unique per host
PORT=3000
DEBUG=false

Questions

The four that come up most often.

Does Rill record or transcode audio?

No. Frames are forwarded without being decoded, so the relay has nothing to record and no codec to negotiate. Mixing, if you want it, belongs in the client.

Where is room state kept?

In memory only, and only while a room has members. There is no database and no file on disk, so a restart is a clean slate.

Why is the endpoint path not /ws?

Because a fixed path turns the relay into something anyone can discover and probe by guessing. The path is derived per deployment and is not published.

Something is broken — where do I report it?

Open an issue with the version line printed at startup and the close code your client saw. Pull requests are welcome; keep them focused and add a changelog entry.
